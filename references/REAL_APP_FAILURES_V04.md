## 勘误与使用限制

### A. 错误 1—3：报错现象与语言原因分开

原文把函数位置、所谓隐式续行、非 ASCII 路径与 `for /f` 等解释写成“真实原因”或“硬性要求”。本轮没有原始故障脚本和同条件 Windows 复现，不把这些解释认定为 VBScript/CMD 的普遍规则，也不据此禁止所有项目使用相应语法。保留原描述待核验；可迁移的是目标环境的实际启动、编码与路径测试，而不是全局“VBS 禁用 On Error”等固定修法。

### B. 错误 4：字符串因果解释有直接反例

原文称 `douyin.com` 会因以 `.qq.com` 结尾而被过滤。本轮用 Python 直接计算：

```python
"douyin.com".endswith(".qq.com")  # False
```

因此所附表达式不支持这段原因解释。该结果不能证明当时没发生误过滤，也没有定位替代根因；实际输入、调用链或其他过滤条件仍需原项目复核。保留原文，不将这条错误解释发布成已证实规则。

### C. 错误 11及旧候选策略：优先级不等于定罪

“网盘一律不能 high”只是该样本当时的修法，不是通用底线。不得只因平台类别判断侵权，但具体分享有足够对应线索时可以优先复核。同样，“平台是知名正版站”“链接是电商”等不自动证明每个对象获授权。真正验收的是依据、对象和人工判断，不是所有项目使用同一分数。

### D. 错误 15及旧导读：索引不是永久能力上限

不得无新依据扩大受理范围，但有新的可靠官方事实和相应验证时可以更新本项目，不必等待公共索引改版。旧索引中的自动化建议不是认证；渠道事实与程序实际能力分别验证。历史“上界”措辞按此理解，不把旧书面流程理解为任何未来线上流程都被禁止。

### E. 错误 23—24：提炼结果要求，不复制唯一实现

错误 23 的要求是声明不超过证据；没有真实提交就不能说真实提交已验证，但可清楚交付待验证实现。不要为获得等级标签向真实平台发送虚构投诉，或未经授权填入/上传真实资料。

错误 24 的要求是当前用户流程有清晰安全的完成、返回或取消途径，不要求统一 Modal、Esc、遮罩行为或任何特定 UI 框架。取消、关闭界面和撤销已发送操作不是一回事。API、UI、目标环境及人工测试分别报告，跳过不计作通过。

- **用户真正会执行的入口必须实测**：测试套件全绿不能替代双击启动、打开 GUI、完成一次真实工作流。

## 一、启动器错误（最严重，用户双击时才发现）

这一类的性质：**软件主体功能测试很细（189 项），但"用户双击能不能打开"这一步没有实测就交付了。**

### 错误 1 · `启动.vbs` 报「无效的 'exit' 语句 / 800A040F」

用户双击后弹出的错误框内容：

```
Windows Script Host
脚本: D:\DeepSeek\jjdd\启动.vbs
行:   49
字符: 10
错误: 无效的 'exit' 语句
代码: 800A040F
源:   Microsoft VBScript 编译器错误
```

**真实原因**：我把 `Function WhereIs(exeName)` 写在了**调用它的主流程之前**。
VBScript 不支持前向引用，函数体里的 `Exit Function` 因此成了非法语句。

**但更深一层的错在我**：为了让 VBS 自己找到 Python，我写死了安装路径：

```vb
candidates = Array( _
  shell.ExpandEnvironmentStrings("%LOCALAPPDATA%") & "\Programs\Python\Python313\pythonw.exe", _
  shell.ExpandEnvironmentStrings("%LOCALAPPDATA%") & "\Programs\Python\Python312\pythonw.exe", ... )
```

而本机 Python 实际在 `C:\Users\示例用户\AppData\Local\Python\pythoncore-3.14-64\`，这些路径全部落空。
于是我又加了一个"搜 PATH"的函数来补救 —— **是自己制造的问题，再用更脆的写法去补**。

**修法**：
1. 函数定义移到脚本末尾（VBScript 的硬性要求）；
2. 彻底不再写死路径，改为扫 `%PATH%` 的每个目录找 `pythonw.exe`，找不到再找 `python.exe`。

### 错误 2 · 改完又报「缺少 'End' / 800A03F6」

用户第二次双击的错误框：

```
Windows Script Host
脚本: D:\DeepSeek\jjdd\启动.vbs
行:   68
字符: 1
错误: 缺少 'End'
代码: 800A03F6
源:   Microsoft VBScript 编译器错误
```

**真实原因**：VBScript 的**隐式行续接**规则。函数里这两行：

```vb
Err.Clear
On Error GoTo 0
```

被解析器当成**一条语句** `Err.Clear On Error GoTo 0`，于是包着它的 `If` 少了 `End If` → 报"缺少 'End'"。
报错行号指向的是"解析到哪才发现不对"，不是"哪一行写错了"，所以第一次定位时被误导过。

**修法**：`启动.vbs` 里**完全不用** `On Error` / `Err.Clear` / `shell.Exec`，只用最朴素的语句
（`%PATH%` 拆分 + `FileExists`），并把这条规则写在文件头。

**验证方式**（不再靠"我觉得应该行"）：

```bat
cscript //nologo 启动.vbs      :: 语法错会打印出来；无输出=语法通过
```

然后实际启动并访问 `/health`，确认返回 `{"ok": true, ...}`，再调 `/api/shutdown` 确认
端口释放、进程退出。

### 错误 3 · `启动.bat` 满屏「不是内部或外部命令」

用户第三次的截图里是这样的（节选）：

```
'鏂囦欢鍚?' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'D:\DeepSeek\jjdd\nu\l') do ( ... ')' 不是内部或外部命令 ...
'...echo' 不是内部或外部命令 ...
```

**两个独立原因同时发作**：

1. **`.bat` 里写了中文**：cmd 按当前代码页渲染，中文变乱码，
   看起来像"软件坏了"；
2. **用了 `for /f`**：

```bat
for /f "delims=" %%I in ('where python 2^>nul') do (
  if not defined PYEXE set "PYEXE=%%I"
)
```

   在用户名或路径含非 ASCII 字符时（本机用户名是 `示例用户`），`for /f` 的解析会崩，
   把括号和半行内容当成命令执行。

**修法**：

- 所有 `.bat` **改成纯 ASCII**——面向用户的中文提示交给 Python 打印（Python 自己写 UTF-8，不乱码）；
- 去掉 `for /f`，改成最笨但可靠的检测：

```bat
python -c "pass" >nul 2>nul
if not errorlevel 1 set "PYCMD=python"
if not defined PYCMD (
  py -3 -c "pass" >nul 2>nul
  if not errorlevel 1 set "PYCMD=py -3"
)
```

- 补上输出编码设置（验证时发现：**输出重定向到文件**时中文仍会乱码，只有这两个变量能同时解决）：

```bat
chcp 65001 >nul 2>nul
set "PYTHONUTF8=1"
set "PYTHONIOENCODING=utf-8"
```

**验证方式**：`启动.bat serve --port 8791 --no-browser` → 访问 `/health` 通过 → `/api/shutdown` 释放端口；
`AI修复\检查工作目录.bat` 的输出重定向到文件后中文正常。

### 错误 4 · 域名跳过用了"字符串结尾包含"

### 错误 5 · 360 搜索解析出相对路径

测试报出：

```
AssertionError: False is not true : 不是绝对地址：
/malurl_tip?m=0ab960d693f8ece88dd42bd0dad56f80&d=&u=https%3A%2F%2Fwww.miaobige.com%2Fshu%2F1007%2F...
```

候选链接不可点，作者点"打开原页面自己看"会打开一个空地址。

**修法**：适配器层统一补齐绝对地址（`urljoin`），并加"契约测试"：
每个解析器返回的链接必须 `startswith(("http://", "https://"))`。

### 错误 6 · 360 取链接固定拿"第一个 a 标签"

结果块的第一个 `a` 是无关的相对链接（`/malurl_tip?...`），真实目标在 `h3` 标题链接的
`data-mdurl` 属性上。

**修法**：遍历 `h3` 下的所有链接，取第一个 `data-mdurl` 是绝对地址的；都没有才退回 `href`。

### 错误 7 · 百度"推荐位"子域名被当成线索

真实结果页里出现 `http://28608.recommend_list.baidu.com`，被收进了候选。

**修法**：保留 `baidu.com` 在跳过表中，同时**显式豁免**真正承载用户内容的子域
（`tieba.baidu.com`、`pan.baidu.com`、`wenku.baidu.com`、`zhidao.baidu.com`），
两侧都加测试。

### 错误 8 · 判定逻辑里运算符优先级写错

```python
# 错误写法：and / or 混在一行，实际语义和我想的不一样
elif discussion_hits and not content_hits and "?" in combined or \
        discussion_hits and not content_hits and any(...):
```

**修法**：抽出具名变量 `strong_discussion`，并把"只有书名相关"这一档的优先顺序重新明确。
同时借此修正了一个**判定倾向错误**：只命中书名的书评页被降到"低优先"，
但业务参考要求这种情况保留为**"相关但待核验"**（作者可自行排除，不能替她降级丢掉）。
现在只有命中「书评/书单/读后感/好看吗…」这类强讨论词才降级，「简介」这类盗文站也常用的词不算。

### 错误 9 · 搜狗整批结果被自己的过滤器丢掉（实测发现）

`python -m mazishouhu sources` 的输出：

```
✓ sogou     搜狗    结果   0 条 HTML  508703 字节
```

取到了 50 万字节页面、解析出 10 个结果块，然后**全部被过滤成 0**。

**原因**：搜狗的结果链接是 `/link?url=...` 跳转包装，域名是 `sogou.com`，
正好命中"跳过搜索引擎自家域名"的规则；而"还原跳转地址"这一步发生在这之后。

**修法**：跳转包装地址先放行，等 `resolve_redirects()` 还原成真实地址后再判断去留；
还原不了的**丢掉并如实报数**（"有 N 条结果没能还原真实地址，已跳过"），
因为留着对作者也没用（点开只是跳转）。

### 错误 10 · 繁简映射表漏字

测试：

```
AssertionError: '測試书名' != '测试书名'
```

`試` 不在手工维护的映射表里，繁体标题匹配不上。

**修法**：补字并加断言 `len(_TRAD) == len(_SIMP)`。
这是**有限映射的固有限制**，不是完整繁简转换，已在代码注释里写明。

### 错误 11 · 网盘/提取码被判成"高优先复核"

自检用例输出：

```
✗ 网盘分享页 → 提示需按具体分享判断，不整站定罪 — 实际level=high, score=7
```

把 `pan.quark.cn/s/xxx` 这种分享页判成"高优先复核"，等于在暗示"这就是盗版"。
业务参考明确要求：网盘/社区类平台**不能整站认定**，要看具体那一条分享。

**修法**：命中用户上传型平台时**不升到 high**（最高 medium），并附加明确理由：
"这条线索出现在用户上传型平台上，是否侵权取决于那一条分享/帖子本身"。

### 错误 12 · 投诉模板 C 静默丢掉一段内容

测试断言失败：草稿里找不到"2 个对象"。

**原因**：多对象时应该插入的"合集范围说明"（*本次主张仅限《作品名》，不代表对其中其他作者的作品享有权利*）
只写进了模板 A/B，模板 C（向主管部门反映）的占位符里漏了 `{collection_line}`。
`str.format` 不会因为多余参数报错，**所以它是静默丢失**——不测就发现不了。

**修法**：模板 C 补上占位符，并加测试：两个对象的批次，草稿里必须出现对象数和"其他作者"字样。

### 错误 13 · Windows 上临时目录删不掉

```
PermissionError: [WinError 32] 另一个程序正在使用此文件，进程无法访问:
'...\mazishouhu-test-xxx\mazishouhu.sqlite3'
```

后台搜索线程还持有 SQLite 连接，测试收尾时就删临时目录。

**修法**：测试里加 `wait_for_search()` 等后台线程结束；清理失败时重试而不是直接判失败
（避免把"删不掉临时文件"误报成"测试失败"）。同时这是**真实场景提示**：
Windows 上软件运行时数据库文件被占用是正常的，用户删除数据前要先退出软件。

### 错误 14 · 改了调用忘了补 import

```
NameError: name 'drop_unresolved_wrappers' is not defined
```

我在 `searchrun.py` 里加了新函数调用，但没同步加 import，6 个测试立刻挂。

**性质**：典型的"漏一步"，不是设计错误。值得记下来是因为**测试立刻抓到了**——
这说明"改完马上跑测试"的习惯确实有效，比事后排查便宜得多。

## 三、业务判断错误（真实数据才暴露）

这是**我认为最有价值的一次**：用自编假数据测试时全绿，一上真实搜索就露馅。

一次真实搜索（百度 + 360，各 6 个检索词）跑出 **97 条候选**。逐条核对"高优先复核"时发现 **10 条误报**：

| 域名 | 旧判定 | 新判定 | 实际是什么 |
| --- | --- | --- | --- |
| `b.faloo.com` | 高优先复核 | 疑似正版 | 飞卢小说网（正版平台） |
| `m.xxsy.net` | 高优先复核 | 疑似正版 | 潇湘书院 |
| `xs8.cn` | 高优先复核 | 疑似正版 | 言情小说吧 |
| `ximalaya.com` | 高优先复核 | 优先复核 | 喜马拉雅（有声书，用户上传） |
| `zhidao.baidu.com` | 高优先复核 | 优先复核 | 百度知道（用户问答） |
| `9game.cn` | 优先复核 | 相关但待核验 | 手机游戏下载站 |

**两个根本原因**：

1. **正版平台表列得太少**——只列了晋江、起点、红袖等十来个，漏掉了 QQ阅读、潇湘书院、
   言情小说吧、飞卢、塔读、磨铁、掌阅等一大批；
2. **盗文站特征词里有含义模糊的短词**——`zhuishu` 会把正版"追书神器"一起命中，
   `shuqi` 会把正版"书旗小说"一起命中。

**修法**：
- 正版平台表补到 20+ 个域名（并写明维护规则：**发现误报就加这里，不要加盗文词表**）；
- 删掉 `zhuishu`、`shuqi`、`yousuu` 这类模糊短词，改成 `zhuishuzw`、`zhuishuku` 这种更具体的；
- 把这次的**真实数据**（域名保留、书名替换成虚构名）固化成回归测试，
  分成"必须高优先"和"绝不能高优先"两组。

**修完复验结果**：

```
级别                    旧     新
高优先复核               34    26
疑似正版/介绍页           44    51

级别发生变化的：10 条
```

26 条高优先**全部是真实小说聚合站，零误报**。

## 五、流程与判断上的错误

这一节没有代码行号，但**比前面任何一条都更该改**。

1. **没有先测启动器就交付**
   我把 189 项测试、真实搜索、证据闭环、投诉草稿全部验证完，却把"双击能不能打开"这种
   最基础的一步留给用户去发现。正确的顺序是：**先确认入口可用，再深入功能**。

2. **对 VBScript 过于自信**
   第一次弹框时我说"重写就好"，结果第二次又弹框。两次都不是环境问题，是我没尊重这门语言的解析规则。
   第三次改成"能不用就不用"，只用最朴素的语句。

3. **一次改动塞太多，没有立刻回归**
   `drop_unresolved_wrappers` 那次是"调用写了、import 忘了"。如果改完立刻跑测试，这个错存在不超过一分钟。

4. **没有尽早用真实数据验证**
   判定规则的 10 个误报，自编假数据永远测不出来。**应该在功能刚能跑通时就上网跑一次真数据**，
   而不是等所有细节都做完。

5. **临时文件乱放**
   探针脚本直接写在项目根目录，交出去之前还得回头清理。以后临时脚本统一放临时目录。

## 七、仍未验证或仍有风险的部分

**不把这些混进"已修复"里，是这份文档的一部分。**

- ⚠️ **启动器是命令行实测，不完全等于手动双击**。我用 `cscript` / `Start-Process` 验证了
  语法与启动结果，但没有"用鼠标双击图标"这一动作的自动化验证。建议作者本人再双击一次确认。
- ⚠️ **搜索源随时可能改版**。目前三个源（百度、360、搜狗）实测可用，
  但百度已经出现过限流；改版后 `adapters.py` 的 XPath 会失效，
  届时用 `python -m mazishouhu sources` 定位。
- ⚠️ **没有登录过任何投诉平台，也没提交过投诉**。百度、夸克等表单是网页应用，
  必填项来自公开指引，**以官方页面当时的实际要求为准**。
- ⚠️ **繁简归一是有限映射**，不覆盖全部繁体字；未覆盖的字仍可能影响匹配。
- ⚠️ **不处理图片盗文、不处理需登录的付费内容**。
- ⚠️ **证据快照不是公证**，也不保证被任何平台采纳。
- ⚠️ **判定规则仍在演化**。这次的 26 条高优先零误报是基于**一部作品、一次搜索**的核对结果，
  换一本书、换一批检索词，仍可能出现新的误报类型。

## 八、一句话总结

这次最贵的教训不是某个语法错误，而是：

> **测试通过 ≠ 用户能用。**
> 189 项测试全绿的时候，用户双击图标看到的却是三个错误弹窗。

所以修完之后立的规矩是两条：

1. **用户真正会做的那一个动作，必须自己先做一遍**（双击、点开页面、走完一遍流程）；
2. **能跑通就立刻上真实数据**——自编的假数据测不出"把正版平台当成盗版"这种错。

## 一、业务路由错误

### 错误 15 · 把“百度版权投诉平台”自行扩大成“百度网盘在线投诉入口”

**发现方式：代码复核 + 直接调用路由函数复现。**

通用工作区里的 `OFFICIAL_CHANNELS.md` 把：

- 百度版权投诉平台；
- 百度网盘公开《权利声明》；

作为两个不同事实来源处理。

其中百度网盘当时已核实的是公开权利声明和书面通知要求；是否能直接通过 `newcopyright.baidu.com` 在线处理百度网盘，明确要求登录后重新验证，不能自行推断。

但本样本生成的运行时 `channels.json` 写成：

```json
{
  "id": "baidu_copyright",
  "entryUrl": "https://newcopyright.baidu.com/",
  "automation": "ASSISTED",
  "accepts": [
    "百度搜索结果中收录的涉嫌侵权页面（请求断开链接）",
    "百度网盘中的公开分享（请求删除分享）",
    "百度贴吧、百度知道、百度文库等百度产品内的用户内容"
  ]
}
```

并把 `pan.baidu.com` 放进这个渠道的 `userContentHosts`。

直接给路由器输入：

```text
https://pan.baidu.com/s/abc
```

会生成：

```text
渠道：百度版权投诉平台
目的：删除网盘中的这个分享
入口：https://newcopyright.baidu.com/
自动化：ASSISTED
```

**问题本质**：

Agent 把“同一家公司的不同产品”自动合并成了一个受理渠道，并把“尚未验证的可能性”写成了运行时能力。

这不是 selector 错误，而是**业务知识被过度推理**。

**防护原则**：

1. `OFFICIAL_CHANNELS.md` 中已经拆开的子产品，不得仅因厂商相同而自动合并；
2. 运行时 `channels.json` 的 `accepts`、`status`、`automation` 不得超过官方索引当前已核验范围；
3. 如果本轮重新登录官方平台并验证出更强能力，可以升级，但要记录：
   - 实际验证日期；
   - 实际产品；
   - 实际表单；
   - 验证到哪一步；
4. “平台入口存在”不等于“这个入口受理该子产品”。

**建议回归测试**：

- 当官方索引把某产品标为 `DRAFT_ONLY/PARTIAL` 时，运行时配置不得无证据提升为更强能力；
- 百度搜索任务和百度网盘内容删除任务必须能够独立路由；
- 同厂商不同产品不能仅凭主域名自动归并。

## 二、安全边界错误

### 错误 16 · “官方域名闸门”用最后两段域名判断同站，`.gov.cn` / `.com.cn` 会误放行

**发现方式：直接调用函数复现。**

投诉自动化执行器声明：

> 真实页面必须落在该渠道的官方域名上，否则拒绝注入任何内容。

但实际 `sameSite()` 的核心逻辑是：

```js
const strip = (h) => h.split('.').slice(-2).join('.');
return strip(ha) === strip(hb);
```

直接测试：

```text
sameSite("https://foo.gov.cn/", "https://www.ncac.gov.cn/")
→ true

sameSite("https://evil.com.cn/", "https://foo.com.cn/")
→ true
```

也就是说，对中国常见多级公共后缀，这个“安全闸门”会把完全无关的站点当成同站。

**问题本质**：

安全边界不能靠“注册域大概是最后两段”这种简化算法。

**建议修法**：

优先使用每个渠道明确维护的：

```text
allowedHosts
allowedSubdomains
```

并按真实 hostname 边界判断：

```text
host == allowed
或
host.endswith("." + allowed)
```

如果未来确实需要自动推导可注册域，应使用可靠的 Public Suffix List / eTLD+1 实现，而不是自己切字符串。

**建议回归测试至少包含**：

```text
www.ncac.gov.cn        → 允许（若该渠道明确列入）
foo.ncac.gov.cn        → 是否允许由渠道配置决定
foo.gov.cn             → 绝不能因为 gov.cn 相同而允许
evil.com.cn            → 绝不能和 foo.com.cn 判成同站
jjwxc.net.evil.example → 绝不能算 jjwxc.net 子域
```

## 三、搜索流程与界面语义错误

### 错误 17 · “跳过这个来源”和“我已处理完，继续”实际调用同一个接口

**发现方式：静态代码复核。**

界面上有两个不同按钮：

```text
我已处理完，继续
跳过这个来源
```

但前端实现中两者都调用：

```text
POST /api/search/:id/continue
```

后端只有：

```text
continue
abort
```

没有真正的“跳过当前来源”语义。

**后果**：

作者以为自己已经跳过当前搜索源，程序却把它当成“验证已经处理完，可以继续这个来源”。

这是典型的：

> **UI 看起来有两个功能，但业务层其实只有一个功能。**

**建议修法**：

为“继续当前来源”“跳过当前来源”“取消整次任务”建立不同命令和状态转换。

**建议回归测试**：

不要只测试按钮存在。必须实际点击后断言：

- continue：继续当前来源；
- skip-source：停止当前来源并进入下一个来源；
- abort：终止整次搜索。

---

### 错误 18 · 四类搜索全部勾选，但查询上限把微博/公众号整组静默截掉

**发现方式：直接调用 `buildQueries()` 复现。**

界面默认允许选择：

```text
网页盗文
网盘文包
微博传播
公众号传播
```

但检索词先按固定顺序生成，再直接：

```js
out = out.slice(0, options.maxQueries);
```

使用四组全选、`maxQueries=6` 时，实际只生成：

```text
测试书名 测试作者        网页盗文
测试书名 全文阅读        网页盗文
测试书名 最新章节        网页盗文
测试书名 网盘            网盘文包
测试书名 txt 下载        网盘文包
测试书名 文包            网盘文包
```

**微博传播和公众号传播一个都没有真正执行。**

如果作品还有曾用名，排在后面的组更容易被挤掉。

**问题本质**：

“用户勾选某能力”不能被内部配额静默取消。

**建议修法**：

至少选择一种：

1. 每个用户勾选的组先保证一个基础检索词，再分配剩余额度；
2. 执行前明确展示“本轮实际会跑哪些查询 / 哪些因额度未执行”并让用户知道；
3. 如果某组完全没有查询，不能把该组显示成“本轮已搜索”。

**建议回归测试**：

- 四组全选 + 小配额时，每个组选中后至少得到一个查询；
- 如果设计上允许某组不执行，UI 必须明确标出“未执行”，不能静默消失。

### 错误 19 · 作者完成验证码后，程序又重新导航原搜索 URL

**发现方式：代码结构确认；尚未在本次样本的真实验证码 E2E 中复现二次拦截。**

搜索被验证码/登录阻断后，程序会暂停给作者本人处理。

作者点击：

```text
我已处理完，继续
```

代码随后执行：

```js
await page.goto(url, ...)
```

也就是重新访问原搜索 URL，再检查一次。

**风险**：

作者刚刚在当前页面完成验证码，重新导航可能：

- 再次触发验证；
- 丢掉验证后的当前结果页面；
- 浪费用户刚刚完成的人工步骤。

**建议修法**：

恢复后先检查**当前标签页**：

```text
当前页面已经是可解析搜索结果
→ 直接采集

当前页仍被阻断 / 页面不对
→ 再考虑导航或提示用户
```

不要把“用户已处理完”自动等同于“重新访问一遍”。

### 错误 20 · “真实零结果”与“解析失败 / JS 空壳 / 限流”区分不够

**发现方式：代码结构确认。**

当前流程能识别部分验证码/登录阻断，也能捕获 `page.evaluate()` 抛出的解析错误。

但如果页面成功加载、没有命中阻断词，而 selector 因改版一个结果都没取到：

```text
raw.length == 0
```

就缺少足够可靠的二次判断来区分：

```text
真的没有搜索结果
搜索引擎改版导致 selector 全失效
拿到的是 JS 壳
返回的是异常页但没有命中现有阻断词
```

同时主搜索流程没有把 HTTP `429 + Retry-After` 作为正式的一等状态处理。

**风险**：

最危险的不是报错，而是把：

> “程序坏了，没解析出来”

展示成：

> “搜索成功，没有盗版结果”。

**防护原则**：

搜索尝试至少应能区分：

```text
ok
empty
blocked
rate_limited
parse_failed
shell_or_unexpected_page
network_error
```

具体状态名不强制，但不能把技术失败伪装成业务零结果。

## 四、环境隔离与安全降级问题

### 错误 21 · 搜索未知站点与官方投诉登录共用浏览器 profile，并会静默 fallback 到 `--no-sandbox`

**发现方式：代码结构确认。**

当前浏览器层复用同一套：

```text
browser-profile
```

用于：

- 搜索引擎；
- 打开疑似盗版站取证；
- 官方投诉平台登录和自动填表。

与此同时，Edge 正常启动失败时，会自动再次尝试：

```text
--no-sandbox
```

CDP 连接失败时也会尝试同样的 fallback。

**风险 1：身份环境混用**

访问各种未知盗文站的浏览器环境，与保存官方投诉平台登录态的环境没有必要完全相同。

更稳妥的设计通常是至少区分：

```text
发现 / 取证 profile
官方投诉 profile
```

**风险 2：安全保护被静默降低**

`--no-sandbox` 会降低 Chromium 的进程隔离保护。

这不应只是“第一次启动失败后的自动补救”，尤其当浏览器会访问未知第三方网站时。

**建议原则**：

- 不静默关闭浏览器沙箱；
- 如果特定环境确实只能这样运行，必须明确说明风险并由用户决定；
- 搜索/取证与官方投诉登录 profile 尽量隔离；
- 具体项目若有充分理由共用，应在维护文档解释原因和风险。

## 五、维护与验收流程问题

### 错误 22 · “从正确 cwd 启动 Harness”被过度等同于“当前 Workspace 已正确选中”

**发现方式：结合既有 Harness 实测经验与本样本启动器实现复核。**

本样本生成了：

```text
启动 Harness.exe
```

它会把 PowerShell 工作目录切换到项目根目录，然后运行 Harness。

这一点是有用的。

但既有真实测试已经确认：

> **Harness 从某个 cwd 启动，不代表 Web UI 一定已经自动注册/选择这个 Workspace。**

因此启动器只能证明：

```text
Harness 进程从正确目录启动
```

不能证明：

```text
Harness Web UI 当前 Workspace 就是这个项目
```

**正确防护**：

每次维修前仍应让作者确认：

```text
当前 Workspace 路径
= 这款软件所在项目根目录
= 能直接看到 AGENTS.md 的那一层
```

此外，本样本的 UI E2E 主要直接启动内部服务进行测试，并不等价于用户真的双击每个启动入口。

这再次印证 v0.4 已经出现过的原则：

> **底层服务能启动 ≠ 用户真正的启动入口已经验证。**

### 错误 23 · 把“允许尝试自动化”标成“这个真实渠道可以自动提交”

**发现方式：修复版交付后的真实用户使用反馈 + 代码/配置复核。**

修复后的软件界面会把渠道大致分成：

```text
第三方网站、360
→ 只整理材料，不自动提交

其他部分官方平台
→ 可以进入自动填表 / 自动提交流程
```

但作者实际使用后发现：

> **界面上被认为“可以自动提交”的平台，实际上仍然无法完成真实自动提交。**

这不是简单的按钮失效，而是**能力验证层级被混在了一起**。

当前程序已经能够确认一些事情：

```text
官方投诉入口在哪里
这个渠道大致受理什么
当前页面属于允许访问的官方域名
程序具备一个通用表单填写器
程序具备上传 / 点击按钮等基础动作
```

但这些事实并不能推出：

```text
这个真实网站登录后的当前表单已经被完整适配
这个多步骤投诉流程能够走到底
这个渠道已经成功完成过真实提交
程序能够识别真实回执
```

**根本原因**：

程序把类似：

```text
channel = VERIFIED / PARTIAL
automation = ASSISTED
```

这样的业务标记，进一步简化成：

```text
canAutomate = true
```

然后 UI 很容易把 `canAutomate = true` 表述成：

> “这个平台可以自动填表 / 自动提交”。

而实际执行器主要仍是**通用表单猜测器**：

```text
寻找“姓名 / 电话 / 邮箱 / 作品名 / 投诉内容 / 链接”等标签
→ 猜附近的 input / textarea
→ 找 file input
→ 找“提交 / 确认提交 / 发送”等按钮
```

这种方法可以辅助简单表单，但不能证明它已经适配：

```text
选择产品
→ 选择权利类型
→ 建立权利作品
→ 添加多个侵权对象
→ 分类别上传材料
→ 法律声明
→ 验证码 / 实名步骤
→ 多页确认
→ 最终提交
→ 回执识别
```

这样的真实多步骤投诉平台。

**这条错误最重要的判断是**：

```text
官方渠道已核实
≠ 自动化已实现

自动化代码存在
≠ 真实表单已适配

模拟页面测试通过
≠ 真实登录后流程通过

真实表单能填
≠ 真实提交已验证

点击过提交按钮
≠ 已确认提交成功

看到成功回执
≠ 后续处理结果已经完成
```

### 建议修法：把“渠道验证”和“自动化验证”彻底拆开

不要再用一个 `ASSISTED` 或一个 `canAutomate` 同时表达所有含义。

可以使用类似下面的双维状态，具体字段名不强制：

```text
channelVerification:
  VERIFIED
  PARTIAL
  UNVERIFIED
```

表示：

> **这个官方渠道、受理范围和入口本身核实到了什么程度。**

再单独维护：

```text
automationVerification:
  UNIMPLEMENTED
  SIMULATED
  REAL_FORM_PARTIAL
  REAL_FORM_READY
  REAL_SUBMIT_VERIFIED
```

含义建议：

- `UNIMPLEMENTED`：没有实现自动填写；
- `SIMULATED`：只在本地 fixture / 模拟页上验证；
- `REAL_FORM_PARTIAL`：在真实官网、真实页面上验证过部分字段或步骤，但不能保证完成全流程；
- `REAL_FORM_READY`：真实登录后的完整表单流程已验证到最终提交前，能够正确填表、上传和处理必要人工步骤；
- `REAL_SUBMIT_VERIFIED`：至少有一次合法、真实、经用户明确确认的投诉完成实际提交，并成功识别真实回执/编号。

**只有 `REAL_SUBMIT_VERIFIED` 才能对作者明确宣称“这个渠道已验证可以自动提交”。**

如果只是：

```text
SIMULATED
REAL_FORM_PARTIAL
REAL_FORM_READY
```

界面应该准确说明：

```text
可辅助填写
已验证到提交前
尚未真实提交验证
```

而不是笼统写：

> “支持自动提交”。

### 关于“通用填表器”

通用填表器可以保留，但它的能力必须降级描述。

例如：

```text
generic form filler
→ 帮助识别和填写简单字段
→ 失败时让作者接管
→ 不能因此把该渠道标成完整自动化
```

如果某个渠道确实需要稳定自动化，可以使用：

- 当前软件内的专用渠道 Adapter；
- 独立浏览器扩展；
- 其他经过真实验证的浏览器自动化实现。

**具体实现方式不强制。**

关键不是“必须用扩展”，而是：

> **渠道能力必须由真实验证证据驱动，不能由代码里是否存在 fill/upload/clickSubmit 函数驱动。**

### 建议回归测试 / 验收要求

至少覆盖：

```text
1. 仅存在通用填表器
→ UI 不得显示“真实自动提交已验证”

2. 仅在 fixture / 本地模拟页跑通
→ automationVerification 最高只能是 SIMULATED

3. 真实官网只验证到打开和登录
→ 不能显示“自动填表已完成验证”

4. 真实表单能填、附件能上传，但没有实际提交
→ 最多 REAL_FORM_READY

5. 只有在用户合法授权、真实提交并识别到回执后
→ 才能标 REAL_SUBMIT_VERIFIED

6. 渠道页面改版、关键步骤变化或长期未复核
→ 自动化状态应能够降级，而不是继续沿用旧的“已验证”
```

界面最好允许作者看到当前能力证据，例如：

```text
夸克投诉平台

官方渠道：VERIFIED
自动化：REAL_FORM_PARTIAL

✓ 官方入口已核实
✓ 当前真实页面能打开
✓ 已验证部分字段填写
✗ 尚未验证完整多步骤流程
✗ 尚未真实提交
✗ 尚未验证回执识别
```

这样用户不会把“程序愿意尝试”误解为“程序保证能完成”。

### 错误 24 · API E2E 全绿，但用户真实 UI 路径存在无法退出的死胡同

**发现方式：真实用户操作发现 + 前端代码复核。**

v0.8 生成样本 `jjdd2` 的现有自动化测试大量通过，但作者实际操作时发现：

> **某个二级菜单 / 弹层打开以后，没有关闭按钮，也无法通过其他方式退出。**

这意味着：

```text
服务端接口正常
API 流程正常
业务数据能创建
测试套件全绿
```

仍然可能出现：

```text
用户点进二级界面
→ 页面能打开
→ 但没有关闭 / 返回 / 取消入口
→ 用户被锁在当前界面
```

**直接原因**：

当前前端的弹层基础机制只提供了：

```text
openModal()
closeModal()
```

但没有把“可退出”做成弹层框架的强制能力。

也就是说，每一个具体弹层都需要开发者自己记得：

```text
写关闭按钮
绑定 closeModal()
```

一旦某个弹层忘记添加，就会形成 UI 死胡同。

同时：

- 没有统一右上角关闭按钮；
- 没有统一 Esc 关闭；
- 普通弹层没有统一点击遮罩关闭；
- 缺少“任何二级界面都必须存在退出路径”的通用验收。

**更深层的原因**：

项目中名为 E2E 的测试，主要覆盖的是：

```text
前端/测试代码
→ 调 API
→ 服务端
→ 数据库 / 业务逻辑
```

而不是：

```text
真实浏览器
→ 用户点击主界面
→ 打开二级菜单
→ 点击关闭 / 返回 / 取消
→ 回到原界面
```

所以它证明的是：

> **API / 服务流程可以走通。**

但没有证明：

> **普通用户可以真正走完并退出 UI 流程。**

这条错误最重要的判断是：

```text
API E2E 通过
≠ UI E2E 通过

页面能打开
≠ 页面可正常使用

按钮存在
≠ 按钮真的能把用户带回正确状态

业务流程能创建
≠ 用户能完成 / 取消 / 返回

自动化测试全绿
≠ 用户不存在导航死胡同
```

### 建议修法：把“可退出”做成 UI 基础能力

不要只针对当前出问题的弹层补一个按钮。

任何 modal / drawer / 二级面板 / 对话框都应该默认具备明确退出机制。

推荐原则：

```text
普通信息弹层
→ 明确关闭按钮
→ Esc 可关闭
→ 可选：点击遮罩关闭

编辑 / 表单弹层
→ 明确“取消 / 关闭”
→ Esc 可关闭（若不会造成数据风险）
→ 未保存内容需要时给出提示

危险操作 / 正在提交 / 数据迁移
→ 可以禁止点击遮罩误关
→ 可以限制 Esc
→ 但仍必须提供清楚、可理解的退出/取消/中止路径
```

不要让“有没有退出入口”依赖每个页面作者临时记得写。

### UI 验收必须真的点击

如果项目有图形界面，交付前至少应对主要二级界面做真实浏览器 UI 测试：

```text
打开主界面
→ 点击入口
→ 二级界面出现
→ 验证内容存在
→ 尝试关闭 / 返回 / 取消
→ 验证二级界面消失
→ 验证主界面恢复可操作
```

至少覆盖：

- 新建；
- 编辑；
- 查看详情；
- 预览；
- 设置；
- 确认提交；
- 错误提示；
- 搜索暂停 / 验证码提示；
- 投诉任务详情；
- 任何 modal / drawer / 二级菜单。

### 建议加入通用 UI 不变量

对所有二级 UI，可以设置类似这样的验收规则：

```text
UI invariant:
任何非主界面状态都必须至少存在一个明确、可测试的退出路径。
```

如果产品设计上确实要求用户暂时不能退出，也必须：

- 明确显示原因；
- 明确显示当前操作状态；
- 提供安全中止或等待完成的机制；
- 不能只是“没有按钮”。

### 建议回归测试

不要只断言：

```text
弹层 HTML 存在
按钮 DOM 存在
API 返回 200
```

还要实际断言：

```text
1. 点击入口后弹层可见
2. 点击关闭后弹层不可见
3. Esc 行为符合该弹层设计
4. 普通弹层点击遮罩行为符合设计
5. 取消后不误保存
6. 关闭后焦点 / 主页面仍可继续操作
7. 每一种二级界面至少有一条退出路径
```

如果使用 Playwright / Selenium / 浏览器自动化，应真正驱动浏览器点击，而不是仅直接请求后端 API。

**特别要避免把“API 端到端测试”命名成“用户端到端测试”而不说明范围。**

更准确的测试分层可以是：

```text
unit
service / API integration
API E2E
UI E2E
真实用户 Smoke
```

每一层解决的问题不同。

## 七、仍未验证或仍有风险的部分

- ⚠️ 本轮没有使用真实作者身份向百度、夸克、UC 等平台提交投诉，因此没有验证真实登录后表单的完整生命周期。
- ⚠️ 错误 19 属于代码级风险：重新导航行为已确认存在，但本轮没有把“作者刚过验证码后立刻再次触发验证码”作为真实事故复现。
- ⚠️ 错误 20 的“JS 壳 / selector 改版误判为空”属于缺少状态防护的结构性风险，不代表所有当前搜索源都已经发生该问题。
- ⚠️ profile 拆分后的实际体验和登录保持策略仍需在 Windows + Edge 环境验证。
- ⚠️ `OFFICIAL_CHANNELS.md` 本身也会过期；它是“已核验事实索引”，不是永远正确的静态真理。真正提交前仍应关注最近核对日期。
- ⚠️ 当前样本仍缺少“合法真实投诉 → 实际提交 → 成功读取回执”的渠道级 E2E，因此不能仅凭通用填表器或模拟测试把任何渠道宣传为 `REAL_SUBMIT_VERIFIED`。
- ⚠️ UI 自动化本身也可能遗漏真实用户路径；即使 UI E2E 通过，仍应至少做一次人工 Smoke，确认主要入口、返回、取消和关闭动作符合实际使用习惯。

## 八、一句话总结

这次最重要的新教训不是“某一行代码又写错了”，而是：

> **参考文档存在 ≠ Agent 一定正确执行参考文档。**  
> **安全闸门存在 ≠ 闸门算法本身就是安全的。**  
> **UI 显示已选择 ≠ 这一类任务真的执行过。**

v0.4 教会我们：

> **测试通过 ≠ 用户能用。**

v0.7 的这个外部样本又补了一句：

> **功能看起来存在 ≠ 业务语义和安全边界真的成立。**

修复后的实际使用又补了一句：

> **程序愿意尝试自动化 ≠ 这个真实渠道已经验证可以自动提交。**

本次 v0.8 样本又补了一句：

> **API E2E 全绿 ≠ 用户真的能从界面里走出来。**
