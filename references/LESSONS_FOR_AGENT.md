# 工程风险与经验索引｜LESSONS_FOR_AGENT.md

文件名保持 `LESSONS_FOR_AGENT.md`。版本：v0.9.1。来自 v0.8.2 同名经验文档及错误 1—24；本轮整理了主题和适用条件，没有重跑历史软件。下列“核验办法”是对现有经验的提炼建议，不是声称已经在所有平台实测。

先按当前任务选相关主题，再读取同一份 [REAL_APP_FAILURES_V04.md](REAL_APP_FAILURES_V04.md)的前置勘误与对应编号。不要整份载入旧案例后把其修法逐条实现；严重安全问题需处理，但具体方案仍应根据当前项目验证。

## 1. 启动、交互与交付入口

**条件**：有普通作者会点击的启动或界面入口。**风险**：服务测试通过，实际启动脚本报错；API 测试通过，二级界面没有退出路径；两个按钮名不同却执行同一动作。**核验办法**：走真实启动入口，打开、取消、返回并再次操作；分别检查跳过、继续、终止的业务效果，明确哪些未在目标设备测。参见错误 1—3、14、17、22、24。

不因此强制 VBS/BAT、纯 ASCII 脚本、特定 Modal、Esc 或遮罩交互；旧 Windows 语法根因中有待核验解释，不能直接当语言规则。

## 2. 搜索结果、目标解析与任务状态

**条件**：有自动采集、分页、二次链接或多检索词。**风险**：跨卡片串值，旧页面引用失效，包装链接还没解析就被当引擎页面丢掉，配额静默挤掉选中类别，恢复时浪费刚完成的验证，失败误记为空。**核验办法**：多个不同结果及中间失败反例；当前页/新页与返回后的身份一致；查询计划和实际执行对应；零结果与未知区分，退让行为符合来源要求。参见错误 5—9、18—20，及旧 PoC 2 经验。

避免把某次 HTTP 失败写成“所有项目必须浏览器采集”，或把一个成功 selector 写成永久适配。需要查询限制时保留实际范围，不强行加量；需要当前页采集时核对目标标签页，不能读到别的任务。

## 3. 候选相关性与真实样本

**条件**：按书名、笔名、域名或内容判断线索。**风险**：同作者其他书混入、短词误报、知名平台被整站豁免或整站定罪、只有自编正例就声称准确。**核验办法**：早期加入少量必要的公开真实样本，并用脱敏反例回归；核对误报和可能的漏报，允许人工纠偏。参见错误 4、7、8、10、11及 v0.4“业务判断错误”。

不要求固定阈值或“网盘最高 medium”。优先复核不等于侵权认定，具体证据足够时可以提高任何平台上具体对象的复核优先级。历史“零误报”只属于记录中的那次样本。

## 4. 接收方、模板与能力声明

**条件**：存在投诉建议、草稿、上传或提交。**风险**：同厂商不同产品错误合并、材料类别混淆、模板静默漏掉权利范围、把通用填表函数当成真实渠道已适配。**核验办法**：核对对象—渠道的正反例、正文与清单完整性、每种材料的目标和数量；将官方事实、实际实现、真实验证分开。参见错误 12、15、23。

官方索引不是永久上限，也不是自动化认证；新依据要能追溯。未真实提交可以标未验证，不为验证造假通知。历史案例本身不决定统一实现；本项目后来由用户明确选定共用成品，当前网页填表须按 [共用接入](SHARED_EXTENSION.md)复用。统一组件仍不代表每个渠道已实测，出现适配问题回共享项目，不在每个作者软件重复修 DOM。

## 5. 授权、浏览器与诊断数据

**条件**：有网页操作、外部内容、材料或模型调用。**风险**：错误同站判断、未批准就读/传材料、搜索环境与投诉资料过度混用、静默降低沙箱、导出诊断夹带秘密或不可信网页指令。**核验办法**：接收范围反例、用户撤销/材料变化、批次串用、秘密扫描和授权前读取检查；实际测保护边界。参见错误 16、21、23及旧 PoC 3 经验。

显式允许的目的地是可选实现之一，但任意子串和末两段比较不足以证明接收方正确。不同 profile、不同目录、忽略文件或权限模式名称也不自动证明强读取隔离；采用何种边界由当前风险决定。

## 6. 维修、并发与可恢复性

**条件**：已有项目或软件内调用 AI 修复。**风险**：每次重做、修错项目、只改源码不更新运行产物、Agent 改评分依据后自报成功、备份回滚覆盖新数据、连接/线程未释放。**核验办法**：复现当前故障，保留现有改动，独立验证修改，核对运行入口和数据恢复边界；受限自动维修还要检查越界修改。参见错误 13、14、22和 [维修参考](AI_REPAIR_GUIDE.md)。

普通维修不必建设完整 orchestrator；受限自动维修需让批准对象与应用对象一致，验证依据不能由维修者随意重新定义。旧 PoC 的合成任务通过不能证明任意网站、任意版本或强沙箱通过。

## 7. 如何增加一条经验

保持同一失败档案路径，用既有错误编号追加或补充现有条目。先写发生条件、现象和证据，再写已复现范围、原因判断、修法及验证；未知不要变成定案，历史解释有误用勘误保留来龙去脉。

单次具体修法通常只留案例；可迁移问题提炼为风险和验收目标。进入核心前检查是否已被现有原则覆盖、是否会锁死方案、能否通过相应测试自行发现。严重且机制明确的安全问题可优先补防线，不必等多个用户受损；不要为了可追溯性把原始私人资料发布进公共档案。
